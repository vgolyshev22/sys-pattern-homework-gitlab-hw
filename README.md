Задание 1. СУБД
Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

Для бюджетирования проектов, формирования финансовой отчётности и прогнозирования рисков лучше всего использовать реляционную СУБД, например PostgreSQL.

Финансовые данные имеют строгую структуру: проекты, статьи расходов, договоры, платежи, бюджеты, плановые и фактические показатели. Между этими сущностями существуют определённые связи, которые удобно описывать с помощью таблиц, первичных и внешних ключей.



1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.
Для лендингов и CRM требования различаются, поэтому для них можно использовать разные типы СУБД.

Лендинги

Для данных, поступающих с лендингов, можно использовать документоориентированную NoSQL-СУБД, например MongoDB.

Формы на разных лендингах могут отличаться. На одном сайте пользователь оставляет имя и телефон, на другом — имя, телефон, адрес электронной почты, тип недвижимости и желаемый бюджет. Документная модель позволяет хранить записи с различным набором полей без постоянного изменения структуры таблиц.

Преимущества такого подхода:

гибкая структура документов;
быстрое добавление новых полей;
удобное хранение JSON-данных;
высокая скорость записи;
возможность горизонтального масштабирования.
CRM

Для CRM лучше использовать реляционную СУБД, например PostgreSQL.

В CRM существуют устойчивые связи между сущностями:

клиентами;
лидами;
менеджерами;
сделками;
объектами недвижимости;
звонками;
встречами;
договорами;
платежами.

Для CRM важны транзакции и целостность данных. Например, сделка должна быть связана с существующим клиентом, объектом и ответственным менеджером.

Таким образом, наиболее обоснованный вариант:

для лендингов — документоориентированная NoSQL-СУБД;
для CRM — реляционная SQL-СУБД.

Данные из лендингов могут сначала записываться в NoSQL-базу, а затем после проверки и обработки передаваться в CRM.



1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.
Для хранения корпоративных норм, инструкций, правил и обучающих материалов можно использовать иерархическую СУБД либо реляционную СУБД с иерархической структурой.


1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

Графовая база представляет информацию в виде:

склады;

Связями могут быть дороги и маршруты:

Склад → Строительный объект

Задание 2. Транзакции
2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

Рассмотрим пополнение баланса телефона банковской картой.

Действие 1. Формирование запроса

Пользователь указывает:

номер телефона;
оператора;
сумму пополнения;
способ оплаты.

Система проверяет формат номера, допустимость суммы и наличие обязательных данных.

Действие 2. Создание операции

Платёжная система создаёт запись об операции с уникальным идентификатором.

Первоначальный статус операции:

CREATED

В записи сохраняются:

идентификатор операции;
номер телефона;
сумма;
время создания;
пользователь;
способ оплаты.
Действие 3. Проверка возможности списания

Банк или платёжная система проверяет:

существует ли карта или счёт;
достаточно ли средств;
не заблокирован ли платёжный инструмент;
не превышены ли лимиты;
не выглядит ли операция мошеннической.

При успешной проверке сумма может быть временно зарезервирована.

Действие 4. Списание денежных средств

Банк списывает или блокирует необходимую сумму на счёте пользователя.

После успешного списания платёж получает статус:

MONEY_DEBITED

Если списание невозможно, операция отменяется.

Действие 5. Зачисление средств оператору

Платёжная система передаёт оператору связи команду на пополнение баланса.

Оператор проверяет номер телефона и увеличивает баланс лицевого счёта на указанную сумму.

После этого оператор возвращает подтверждение об успешном зачислении.

Действие 6. Завершение транзакции

После подтверждения оператора платёжная система:

фиксирует успешный результат;
устанавливает статус COMPLETED;
сохраняет время завершения;
формирует чек;
отправляет пользователю уведомление.

Транзакция объединяет несколько операций в единое целое. Её смысл заключается в том, что либо все необходимые действия успешно фиксируются, либо изменения отменяются.

Если деньги были списаны, но оператор не подтвердил пополнение, система не должна просто считать операцию успешной. Возможны следующие действия:

повторная отправка запроса оператору;
проверка состояния операции по идентификатору;
возврат или разблокировка денег;
перевод операции на ручную обработку.

На практике списание денег и пополнение баланса происходят в разных информационных системах, поэтому одна общая транзакция базы данных невозможна. Для согласованности используются уникальные идентификаторы операций, журналирование, повторные запросы и компенсирующие операции.

Задание 3. SQL vs NoSQL
3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

1. Строгая структура данных

В SQL-системах данные хранятся в таблицах с заранее определёнными столбцами и типами данных.

Например, в поле суммы нельзя случайно сохранить произвольный текст, если столбец имеет числовой тип.

Это упрощает контроль качества данных.

2. Обеспечение целостности

SQL-СУБД позволяют применять:

первичные ключи;
внешние ключи;
ограничения NOT NULL;
ограничения UNIQUE;
проверки CHECK.

Благодаря этому база данных самостоятельно контролирует корректность связей между сущностями.

3. Полноценная поддержка транзакций

Реляционные СУБД обычно хорошо поддерживают ACID-свойства:

Atomicity — атомарность;
Consistency — согласованность;
Isolation — изолированность;
Durability — долговечность.

Например, при банковском переводе нельзя списать деньги с одного счёта и не зачислить их на другой.

PostgreSQL объединяет несколько действий в одну транзакцию и позволяет завершить их командой COMMIT либо отменить командой ROLLBACK.

4. Сложные запросы и связи

SQL позволяет:

объединять таблицы с помощью JOIN;
выполнять группировку;
использовать вложенные запросы;
рассчитывать агрегаты;
применять оконные функции;
строить сложные отчёты.

Это особенно важно для финансовой аналитики, CRM и отчётности.

5. Стандартизированный язык

SQL является общепринятым языком работы с реляционными базами данных.

Хотя конкретные СУБД имеют свои расширения, базовые команды похожи:

SELECT
INSERT
UPDATE
DELETE
CREATE TABLE
JOIN
GROUP BY

Это упрощает обучение специалистов, интеграцию систем и перенос запросов между различными реляционными СУБД.

Задание 4. Кластеры
Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

В условии требуется обрабатывать огромный объём данных и выполнять большое количество вычислений на кластере из 1000 машин.

Основным критерием выбора должен быть характер нагрузки.

Необходимо определить:

какие данные обрабатываются;
можно ли разделить задачу на независимые части;
требуется ли обработка транзакций;
насколько важна строгая согласованность;
что важнее — скорость записи, скорость аналитики или сложные вычисления;
необходимо ли обрабатывать данные в реальном времени;
можно ли хранить данные распределённо;
как система должна переживать отказ отдельных машин.

Если главная задача заключается не в обработке отдельных транзакций, а в массовом анализе огромных наборов данных, следует выбирать распределённое хранилище или аналитическую СУБД, поддерживающую горизонтальное масштабирование.

Наиболее подходящей моделью распределённых вычислений для пакетной обработки будет MapReduce.

Принцип работы MapReduce
Этап Map

Общий набор данных делится на части. Каждая машина обрабатывает свою часть независимо.

Например, необходимо подсчитать количество операций по каждому строительному объекту.

Один узел формирует промежуточные данные:

Объект А → 1
Объект Б → 1

Другой узел:

Объект А → 1
Объект В → 1

Такую обработку одновременно выполняют сотни или тысячи машин.

Этап Shuffle

Система группирует результаты с одинаковыми ключами:

Объект А → [1, 1]
Объект Б → [1]
Объект В → [1]
Этап Reduce

Полученные значения объединяются:

Объект А → 2
Объект Б → 1
Объект В → 1
Почему MapReduce подходит

MapReduce подходит по следующим причинам:

задача делится на множество независимых частей;
вычисления выполняются параллельно;
можно использовать все 1000 машин;
данные могут храниться рядом с узлами, которые их обрабатывают;
отказ одной машины не приводит к потере всей задачи;
невыполненный фрагмент можно запустить повторно на другом узле;
объём обрабатываемых данных может масштабироваться вместе с размером кластера.

Однако MapReduce лучше подходит для пакетной обработки и не всегда эффективен для интерактивных запросов, поскольку промежуточные результаты могут записываться на диск.

Для многократных вычислений над одними и теми же данными более эффективной может быть модель вычислений в памяти, например Apache Spark. Она позволяет повторно использовать промежуточные данные без постоянного чтения с диска.

Итоговый выбор может быть следующим:

для пакетной обработки огромных файлов — Hadoop и MapReduce;
для быстрой аналитики и повторяющихся вычислений — Apache Spark;
для SQL-аналитики — распределённая колоночная или MPP-СУБД;
для потоковой обработки — специализированная stream-processing-система.

Для описанного случая наиболее обоснованным базовым ответом будет распределённая СУБД или файловое хранилище с горизонтальным масштабированием и модель MapReduce. Если требуется более высокая скорость повторных вычислений, предпочтительнее использовать Apache Spark.
Приведите ответ в свободной форме.
